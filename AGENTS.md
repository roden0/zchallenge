# AGENTS.md

Guidance for AI coding agents working in this repository. Humans: this is also the shortest summary of how the project is built.

## Project

Mobile phone catalog web app (technical challenge). Three views: **catalog list** (grid + live search), **product detail** (color/storage selectors, dynamic price and image, similar products) and **cart** (persistent, removable items, total).

- `apps/web`: React SPA (the UI).
- `apps/bff`: Express Backend for Frontend. The only thing that talks to the upstream phones API.

Requirements that are graded and must never regress: responsive layout, accessibility, **clean browser console (no errors or warnings)**, tests, linting/formatting, a detailed README, and distinct dev (unminified) and production (concatenated + minified) modes.

## Workflow: spec first, always (OpenSpec)

Every feature goes through OpenSpec. Do not write feature code without an approved change.

1. `/opsx:explore` (optional) to think through an idea.
2. `/opsx:propose <verb-led-change-id>` creates `openspec/changes/<id>/` with `proposal.md`, delta specs, `design.md` (only when there is a real decision) and `tasks.md`.
3. **Stop and wait for human review of the proposal.** Do not apply until it is approved.
4. `/opsx:apply` implements `tasks.md` in order. Tick each task only when it is actually done and verified.
5. `/opsx:archive` once merged-ready, so delta specs are folded into `openspec/specs/`.

Rules:

- One change = one branch = one PR. Keep changes small and vertical.
- Specs describe observable behavior as requirements with `#### Scenario:` blocks (WHEN/THEN). No implementation details in specs; those go in `design.md`.
- If a task reveals the spec is wrong or ambiguous, update the change artifacts first, then continue. Do not silently deviate.
- Exempt from the flow: typo fixes, dependency bumps, formatting-only commits.
- Do not edit the OpenSpec-managed block of this file if `openspec init` adds one, nor files under `.claude/`, `.cursor/` or similar generated by `openspec init/update`.

## Commands

> Target scripts. They are created by the `setup-monorepo-tooling` change; until then they may not exist.

```bash
pnpm install
pnpm dev            # web + bff, assets NOT minified
pnpm build          # production build: concatenated + minified assets
pnpm start          # serve the production build
pnpm lint           # Biome check
pnpm format         # Biome format --write
pnpm typecheck      # tsc --noEmit in every package
pnpm test           # Jest + RTL (web), Mocha + Chai (bff)
```

**Definition of done for any task:** `pnpm lint`, `pnpm typecheck` and `pnpm test` pass, and the app runs in the browser with an empty console. Report what you actually ran. Never claim something works if you did not execute it.

## Stack

pnpm workspaces + Turborepo, Biome (lint + format), TypeScript (`strict`), React 19 with function components and hooks, Rsbuild, Express on Node 18, Context API + `useReducer` for state, CSS Modules with CSS variables, Jest + React Testing Library (web), Mocha + Chai (bff).

- The challenge mandates Node 18. Before pinning any tool version, check that it supports Node 18.
- **Do not add a dependency without asking.** Prefer the platform and the existing stack. State why, and what the alternative was.

## Architecture

```
apps/web/src/
  app/        router, providers, entry
  features/   catalog/  product-detail/  cart/   (each: components, hooks, state, api, tests)
  shared/     components, hooks, api client, utils, types
  styles/     css variables, reset, globals
apps/bff/src/
  routes/  services/  middleware/  config/
```

- Group by feature, not by file type. A feature may import from `shared/`, **never from another feature**. If two features need it, move it to `shared/`.
- `web` only calls the BFF, never the upstream API.
- The BFF owns the `x-api-key` header, read from an environment variable. The key must not appear in client code, logs, commits, specs or this file.
- Normalize upstream data in the BFF (or one mapping function in `web/shared`), not scattered across components.
- API contract notes live in `docs/api-notes.md`. Read it before touching data code. If a behavior is not documented there, verify it against the real API and document it. **Do not guess response shapes.**

## Code conventions

- TypeScript: no `any`, no non-null `!` without a comment, no `@ts-ignore`. Prefer `unknown` plus narrowing at boundaries. Model variants with discriminated unions.
- React: function components, named exports, small components, props typed explicitly. Derive state instead of duplicating it (for example, selected color and storage are state; displayed price and image are computed from them).
- Effects: only for synchronization with external systems. Data fetching hooks must cancel stale requests with `AbortController` and expose `loading | error | success` states.
- Keys in lists must be stable and unique. Check upstream data for duplicate ids before relying on them.
- Styling: CSS Modules, design tokens as CSS variables in `styles/`. No inline styles for static values. Font stack is exactly `Helvetica, Arial, sans-serif` with the weights from `docs/design-notes.md`. CSS variable names mirror the Figma token names (`SDS/...`), and all values come from `tokens.css`.
- Naming: components `PascalCase.tsx`, hooks `useThing.ts`, everything else `kebab-case`. Code, comments, commit messages and specs in English.
- No dead code, no commented-out code, no `console.log`, no `TODO` without a linked task in `tasks.md`.
- Follow the existing code before inventing a new pattern. Biome decides formatting; do not argue with it.

## State and cart

- Global state with Context API + `useReducer`. Keep the reducer pure and exported for testing.
- The Figma has no quantity control, and the API has no color code or SKU. How repeated additions of the same configuration behave is defined in the cart spec (see `docs/design-notes.md`, section "Proposed"). Follow the spec. Every line must be removable individually.
- Persist to `localStorage` under one versioned key. **Treat stored data as untrusted**: validate on read, fall back to an empty cart on corrupt data, and wrap access in try/catch.
- The navbar badge shows the number of items and is announced to assistive tech.

## Accessibility (checked on every UI change)

- Semantic HTML first (`nav`, `main`, `ul`, `button`, `a`, headings in order). ARIA only when HTML cannot express it.
- Everything usable by keyboard with a visible focus style. Selectors for color and storage are real form controls or correct radio groups, with labels.
- Informative images have meaningful `alt`; decorative images use `alt=""`.
- The search results counter uses a polite live region. Loading, empty and error states are announced.
- The "Add to cart" button is genuinely disabled until color and storage are chosen, and the reason is discoverable.
- Respect `prefers-reduced-motion`. Verify color contrast against the Figma palette.

## Testing

- Test behavior, not implementation. Query with RTL by role, label and text; use `userEvent`. No snapshot tests.
- Always covered: cart reducer (add, duplicate, remove, total, hydration from corrupt storage), search debounce and result count, detail selectors (price/image change, button enablement), cart view, BFF routes (success, upstream error, missing key, query params).
- Mock at the network boundary, not by stubbing internal modules.
- **Never edit or delete a test to make it pass** unless the spec changed. Say so explicitly if it did.
- A bug fix starts with a failing test that reproduces it.

## Git

- Branches: `feat/<change-id>`, `fix/<short-name>`, `chore/<short-name>`.
- Create one branch per OpenSpec change (`feat/<change-id>` for features, `chore/<change-id>` for tooling) and make the finishing commit — a brief description of the changes — before archiving it. Merge the branch once reviewed.
- Conventional Commits (`feat(cart): ...`, `test(bff): ...`). Small, atomic commits that each leave the repo green.
- Every PR has a description: what and why, link to the OpenSpec change, how it was verified, and what AI agents did versus what was reviewed by hand.
- Do not rewrite shared history or push to `main` directly.

## Working agreements for agents

- Read `openspec/config.yaml`, the relevant specs in `openspec/specs/`, and the active change before writing code.
- Ask when a requirement is ambiguous or the Figma/spec conflict. Otherwise state your assumption in one line and proceed.
- Keep diffs focused. Do not refactor unrelated code in the same change.
- Do not make visual decisions from memory. `docs/design-notes.md` is the visual reference (layout, states, hover, copy, known Figma inconsistencies). Colors, sizes and spacing come from CSS variables extracted from Figma. If a value is marked `[CONFIRM]` or is missing, ask instead of inventing it.
- UI strings live in one module (`shared/strings.ts`). Do not scatter literals through components.
- Out of scope unless a change says otherwise: SSR, deployment, feature flags. They are optional extras for later changes.
- Be honest in summaries: list what was done, what was verified, and what was not.
